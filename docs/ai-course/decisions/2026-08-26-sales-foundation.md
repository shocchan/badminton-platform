## 0. いちばん重要な制約（作業前に判明した事実）

### staging と本番は同じデータベースを共有している

`.env.staging` は `VITE_SUPABASE_URL` を上書きしていない。したがって
`.env` の本番プロジェクト（`jdkwij…`）を staging も使う。

**結果として起きること:**

| 対象 | staging に出すと本番はどうなるか |
|---|---|
| Cloudflare Pages（フロント） | 影響なし（別デプロイ） |
| DBマイグレーション | **本番DBに即反映** |
| Edge Functions | **本番に即反映**（環境ごとに分かれていない） |
| ai_config | **本番に即反映** |

このため今回は次の規律で作業した。

- マイグレーションは**加算のみ**。列の削除・テーブルの削除・破壊的変更をしない
- 既存の行を書き換えない（`ai_config` の体験パス枠だけは意図的に更新。理由は §2）
- **Edge Functions はデプロイしない**（本番の挙動が変わるため）
- 計測は `is_test` で staging 分を分け、集計から外す

### staging も本番の Stripe（live）を使う

`.env.staging` に `VITE_AI_COURSE_CHECKOUT=live`。
決済ページの生成までは確認できるが、**実際の支払いは行っていない**。
「購入 → webhook → 受講権発行」の一気通貫は、実際のお金を動かさずには確認できない。
報告では確認できた範囲と、できていない範囲を分けて書く。

## 1. 計測（S1）— 既存イベントを潰さずに、断絶をつなぐ

### 何が壊れていたか

計測が2つに割れていて、**断絶がちょうどお金の判断に必要な位置**にあった。

| | 未ログイン（LP・CTA・checkout） | ログイン後（学習） |
|---|---|---|
| `ai_lp_views` | 書ける（ただし1ブラウザ1日1行） | — |
| `ai_course_events` | **書けない**（auth必須） | 書ける |

実測: 記録されたLP閲覧7件はすべてUTMなし。8月のMeta広告 ¥1,992 は申込0件だったが、
そもそも広告経由の閲覧があったのかも判別できない。

### どうしたか

`ai_attribution`（ブラウザ単位の first-touch / last-touch）と
`ai_funnel_events`（未ログインから購入後まで同じ `anon_id` で並ぶ出来事）を追加。

**first と last の両方を持つ理由:** 中国語圏の導線は
「小紅書で知る → 何日か考える → WeChat のリンクから買う」が普通で、
last-touch だけ見ると常に WeChat が全部の手柄を持っていく。

**新しいイベント名を並べなかった理由:** 仕様が挙げた13種のうち12種は、
既にGA4側に同じ意味の名前があった。並べると同じ行動が二重に数えられる。
`track()` / `trackCourse()` の中で対応づけ、新設は `review_scheduled` だけ。

| 仕様の名前 | 使った既存イベント |
|---|---|
| ai_course_lp_view | `view_ai_course_lp` |
| ai_course_cta_click | `click_ai_course_to_pricing` ほかCTA系 |
| trial/monthly_checkout_start | `begin_checkout`（plan で分岐） |
| six_month_checkout_start | `begin_ai_course_application` |
| purchase | `purchase` |
| trial_activated | `start_ai_course_trial` |
| lesson_started / lesson_completed | `start_/complete_ai_course_lesson` |
| review_scheduled | **新設**（同義のものが無かった） |
| review_completed | `complete_ai_course_daily_review` |
| upgrade_cta_view / click | `view_ai_course_upsell` / `click_ai_course_trial_end_plan` |

### 個人情報

`anon_id` はブラウザが作る乱数UUID。氏名・メール・IP・UserAgent・URL全体は
保存も送信もしない。referrer は**ホスト名だけ**。GA4 へ渡すのも source/medium/campaign まで。

`anon` が実行できるRPCなので、kind をホワイトリストで縛り、UUID形式・120文字・
1日300行で制限した。形が違うものは**例外を投げずに捨てる**（計測の失敗で画面を壊さない）。

## 2. 体験（S2）— 60分では、この商品の中心を体験できなかった

### 事実

`ai_start_trial` は `valid_until = trial_started_at + 60分` を書く。実時間で同じ日に終わる。
一方この商品の中心は間隔反復で、復習は翌日以降に届く。

実測（唯一の体験購入者・2026-08-19）:

| 項目 | 実測 |
|---|---|
| 会話 | 2回・合計199秒 |
| 復習予定に入った表現 | 4個 |
| **実際に届いた数** | **0個** |

### 変更

開始から7日間へ。**価格は据え置き。**

### AI原価 — 当初の判断は誤りだった

最初「音声は合計回数で頭打ちだから原価は増えない」と考えたが、
これは**テキスト会話について誤り**。テキストは1日あたりの上限しかないので日数ぶん伸びる。

`planAiBudget` の最悪値モデルで検算（600円・方針の上限は原価率60%＝¥360）:

| 設定 | 音声 | テキスト | 合計 | 原価率 |
|---|---|---|---|---|
| 旧 60分・テキスト10/日 | ¥300 | ¥0 | ¥300 | 50.0% |
| 7日・テキスト10/日 | ¥300 | ¥52 | ¥352 | 58.7% |
| **7日・テキスト5/日** | ¥300 | ¥26 | **¥326** | **54.3%** |

テキストを 10 → 5/日 にした。音声3回が主で、テキストは補助なので体験の中身は落ちない。
あわせて音声を1日2回までにした（合計3回は不変）。初日に使い切ると翌日の復習に
出会えないため。**もらえる回数は減っていない。**

### ついでに直したバグ

`planAiBudget` が日数を `accessDays`（＝**開始の期限**30日）にフォールバックしていた。
そのため体験パスの原価率が87%と出て、実際には起こりえない赤字で商品を殺すところだった。
`trialDays` を見るよう修正。

### 既存を壊さない作り

新しい関数を作らず `ai_start_trial` を置き換え、`trial_days` を優先して
無ければ従来の分数にフォールバックする。**本番のフロントは（承認まで）古いままだが、
古いフロントが呼んでも `trial_days` があれば7日になる**ので、
「LPは7日と書いてあるのに60分で切れる」という食い違いが起きない。
開始済みの行（`trial_started_at` が入っている行）には一切触らない。

## 3. LP（S3〜S5）— 価格より前に、選ぶ理由を出す

価格表が6番目・人間コーチの紹介が9番目だった。
読む人は、この商品の**唯一の代替できない部分**を見る前に金額を見ていた。
中国語圏には安価で高機能なAI会話アプリが大量にあるので、その状態で価格を出すと
「AIアプリなのに高い」という比較で終わる。

新しい並び:

```
悩み → 日本生活の場面 → なぜAIアプリだけでは足りないか → 仕組み
→ AIと人の役割 → コーチ紹介 → 学習サイクル → 600円体験
→ 6か月ロードマップ → 料金 → 比較・向き不向き → 受講生 → FAQ → 最終CTA
```

「なぜAI会話アプリだけでは足りないのか」を新設。**競合名は出さず、攻撃もしない。**
AIが得意なことと、AIには決められないこと（何を練習するか・忘れた頃に出し直す・
続ける理由・日本での自分の場面）を事実として分けて書いた。

- **6か月（S4）**: 「AI＋レッスン24回」という部品の足し算をやめ、
  「日本で暮らしながら日本語を使えるようになるまでの伴走」と書いた。上達は保証しない。
- **月額（S5）**: 削除も値下げもしない。「人のレッスンは要らない。自分のペースで
  続けたい人」と位置づけを言葉で固定した。

順序は1行の移動で戻せてしまうので `lpOrder.test.ts` で固定している。

## 4. 体験終了（S6）と 声（S7）

- 終了画面に、実測の「直してもらった言い方」「復習した回数」「いちばん練習の
  余地がある表現」を追加。**直したあと（improved）だけ**を出し、
  本人が言った文は出さない（買うかどうかを決める場所で失敗を並べない）。
- 「いちばん弱い」は比べる相手が1つしか無いときは言わない。
- 声は**許諾を感想と別チェック・既定OFF**で集める。許諾があっても自動公開しない。
  許諾が無い行は管理者でも承認できない（サーバー側で拒否）。氏名・メールは保存しない。

## 5. 本番へ出すときの手順（承認後）

順番が重要。**フロントと Edge Functions は同時に出すこと。**

1. マイグレーションは**適用済み**（本番DB共有のため既に反映されている）
   - `20260826140000_ai_funnel_attribution`
   - `20260826150000_ai_trial_seven_days`
   - `20260826160000_ai_testimonials`
   - `20260826170000_ai_admin_purchases_attribution`
2. Edge Functions を出す（**まだ出していない**）
   ```
   supabase functions deploy ai-course-checkout
   supabase functions deploy ai-course-stripe-webhook
   ```
   - `ai-course-checkout`: 購入行に `anon_id` と流入元を焼き付ける
   - `ai-course-stripe-webhook`: 受講権に `trial_days = 7` を書き、購入メールを日数で案内する
   - **これを出すまで、新しく買った人の受講権は `trial_days` が null＝旧仕様の60分**
3. フロントを出す（`scripts/deploy-production.sh`）
4. 出したあとに確認する
   - `/ja/ai-course` `/zh/ai-course` が並び替え後の順で出るか
   - 管理画面に「販売ファネル」「受講者の声」が出るか
   - `ai_funnel_events` に `is_test = false` の行が入り始めるか

### 戻し方

| 戻したいもの | 方法 |
|---|---|
| 体験を60分へ | `20260826150000_…rollback.sql`。**開始前の人だけ**なら `update ai_course_access set trial_days = null where trial_started_at is null;` |
| 計測をやめる | `20260826140000_…rollback.sql`（表ごと消えるので、止めるだけなら関数の revoke だけにする） |
| 声を集めるのをやめる | `20260826160000_…rollback.sql`（既定では表を残す＝許諾の証跡を消さない） |
| フロント | 直前のコミットで再デプロイ |

## 6. 確認できていないこと（正直に）

- **実際の支払いを伴う一気通貫**（購入 → webhook → 受講権 → 自動ログイン → 体験開始）。
  staging も本番Stripeを使うため、確認には実際の課金が要る。決済ページの生成と
  支払い方法の表示までは確認済み。
- **Alipay / WeChat Pay での支払い完了**。同上。
- **7日間の経過による自動終了**。時間の経過そのものは待つしかない。
  RPCが `valid_until` を「開始+7日」に書くところまでは検算済み。
- **Edge Functions の実行時の挙動**。Deno がこの環境に無く、本番共有のためデプロイもしていない。
  ソースの形は `edgeFunctionContract.test.ts` で固定している。
