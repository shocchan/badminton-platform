## 2. 出す手順

```bash
cd /Users/shocchan/badminton-sales && ./scripts/deploy-production.sh
```

これだけ。スクリプトが前提条件を全部チェックし、
1つでも欠けていれば**中断する**（本番には触れない）。

動かして確かめたいだけのときは、アップロードを飛ばせる:

```bash
DRY_RUN=1 ./scripts/deploy-production.sh
```

`DRY_RUN=1` は②アップロードを飛ばすだけで、**チェックは全部通る**。
チェックを飛ばす手段は用意していない。

## 3. 実行前に通るチェック（1つでも×なら中断）

| | 見るもの | 中断する理由 |
|---|---|---|
| (a) | いまのブランチが `scripts/DEPLOY_BRANCH` と一致するか | 別ブランチから出すと、そのブランチに無いものが本番から消える |
| (b) | `src/ supabase/ scripts/ public/` に未コミットが無いか | 未コミットのまま出すと、本番の中身がどのコミットなのか誰にも分からなくなる（実際に起きた） |
| (c) | 他ブランチに未取込の `src/` 変更が無いか | 取り込み忘れたまま出すと、その変更が本番から消える |
| (d) | 他のフォルダ（worktree）に未コミットの `src/` 変更が無いか | コミットされるまでこのブランチに来ない＝「直したのに本番に出ない」 |

(c) は **最終コミットが90日以上前のブランチを除外**する。
放棄されたブランチのせいで永久に止まり、結局チェックごと外される――を避けるため。
除外したブランチ名と最終コミット日は毎回画面に出す（黙って無視しない）。

中断のときは「どうすれば進めるか」を具体的なコマンド付きで出す。

## 4. 新しく作業を始めるときの決まり

1. **枝はデプロイ用ブランチから切る**
   ```bash
   cd /Users/shocchan/badminton-sales
   git switch integration/unify-2026-08-28
   git switch -c feature/<やること>
   ```
2. 作業してコミットする
3. **終わったらデプロイ用ブランチへ戻す**
   ```bash
   git switch integration/unify-2026-08-28
   git merge feature/<やること>
   ```
4. 出すのは 2. の1コマンド

長生きする枝を作らない。作業が終わったら戻す。
戻していない枝は (c) で毎回引っかかり、デプロイが止まる。

## 5. 2026-08-28 に何が起きたか

Cloudflare Pages の配信は**差分ではなく全置換**である。
アップロードしたフォルダの中身が、そのまま本番サイトの全体になる。

当時、本番のビルド元がワークツリー4つに分かれ、それぞれ別ブランチを開いていた。
`scripts/deploy-production.sh` は**どのフォルダからでも実行できた**ので、
実行した人のフォルダの姿へ本番が丸ごと入れ替わった。

- 同日だけで**3回**、本番が別フォルダの姿に上書きされた
- そのうち1回で **AIコースのログインが消え、実在の生徒3人がログインできなくなった**
- 本番が**未コミットの作業ツリー**から作られていた回もあった

## 6. なぜ「警告」ではなく「中断」にしたか

事故当時のスクリプトにも、取り残しを知らせる仕組みはあった。
ただし**警告を出すだけで、そのまま続行していた**。

警告は読み飛ばされる。実際に読み飛ばされて、生徒が入れなくなった。
出るかどうかではなく、**止まるかどうか**でしか事故は防げない。

同じ理由で `--force` のような抜け道は作っていない。
**抜け道があれば必ず使われる。** 急いでいるときほど使われる。

止まったときは、画面に出ている手順どおりに取り込んでから、もう一度実行すること。
